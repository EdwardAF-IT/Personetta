# Personetta — product requirements

This document records **non-negotiable** goals for Personetta. Without satisfying these, the system is only an academic exercise; the generator and install paths must be judged against this list.

## R1 — Global defaults, local overrides

- **Global rules apply by default** across workspaces so the author does not reinstall the same roles every time a new repository is opened.
- **Local (project) rules** may override or extend global rules when present. Precedence: project-specific installed or linked rules win over the user-wide install when the tool defines such layering.
- **Mechanism today:** `personetta install '*' --format <fmt>` defaults to `--target global` (user home). For **Cursor**, the CLI also merges the same rule text into Cursor’s global User Rules store (`aicontext.personalContext`) so the Agent sees personas in every workspace without per-repo installs, and copies bundled Agent skills from `.cursor/skills/` into the user’s global `~/.cursor/skills/` on each successful `install '*' --format cursor`. For **Claude Code**, the CLI copies skills from `.claude/skills/` into `~/.claude/skills/` on each successful `install '*' --format claude` (skippable with `PERSONETTA_SKIP_CLAUDE_SKILLS`). **GitHub Copilot** and **Cline** do not use the same “skills” surface as Cursor/Claude Code; their always-on instructions / global rules are the primary delivery. Use `personetta link …` with `--format <fmt> --project <path>` to junction/symlink a project path to the global install (Cursor: `.cursor/rules`; Copilot: `.github/instructions` → `~/.copilot/instructions`; Claude: `.claude/rules`; Cline: `.clinerules` → `~/Documents/Cline/Rules`), or `--target project` to write only into one repo (skips Cursor User Rules sync; global Cursor skills under `~/.cursor/skills/` are still refreshed from `.cursor/skills/` when format is Cursor).

## R2 — Generated roles are “on” (without loading every persona at once)

- Installed roles must be **effective** without hunting for opt-in toggles in the host UI. That does **not** mean every recipe file should be `alwaysApply: true` simultaneously—merging dozens of full personas confuses the model and wastes context.
- **Cursor layout (required):**
  - **`personetta-baseline.md`** in `.cursor/rules/` — thin, **always on** cross-cutting rules (tools first, surface model recommendation, honor verification, single active persona).
  - **`personetta-router.md`** in `.cursor/rules/` — recipe index (ids, summaries, **`activation_phrases`**, **`set-active`** hints). **`alwaysApply: false`** so it is merged when contextually relevant, not on every message (reduces noise vs baseline + active).
  - **`personetta-active.md`** in `.cursor/rules/` — **one** full composed recipe, **`alwaysApply: true`**, replaced when the user runs **`set-active`** (only baseline + active use **`alwaysApply: true`** among Personetta rules).
  - **`.personetta/cursor-recipes/<recipe>.md`** — full bodies for all recipes (cache; not treated as separate Cursor rules). Regenerated by `install '*'` / `recipe --install`. After each successful `install '*'`, the cache is **pruned** to match recipes that composed successfully (so `--filter` runs and removed recipes do not leave stale `.md` files). If **no** recipe succeeds, Personetta **removes** baseline, router, active, cached bodies, and `cursor-active.json` on that target so a prior persona cannot linger next to a failed run.
- Switch persona (same UX for every format): `personetta set-active <recipe> --format <cursor|copilot|claude|cline>` (same `--target` as install).

- **GitHub Copilot (VS Code) layout (required):** User-scope always-on instructions under **`~/.copilot/instructions/`** as `*.instructions.md` with YAML frontmatter and `applyTo: "**"` (see VS Code custom instructions). **`personetta-baseline.instructions.md`**, **`personetta-router.instructions.md`**, **`personetta-active.instructions.md`**; full recipe bodies cached under **`.personetta/copilot-recipes/<recipe>.md`**. State: **`.personetta/copilot-active.json`**. Implemented in `generator/copilot_layout.py`.

- **Claude Code layout (required):** User rules under **`~/.claude/rules/`** as markdown: **`personetta-baseline.md`**, **`personetta-router.md`**, **`personetta-active.md`** (loaded every session per Claude Code memory docs). Cache: **`.personetta/claude-recipes/<recipe>.md`** (Copilot-shaped markdown for readability in rules files). State: **`.personetta/claude-active.json`**. Legacy **`~/.claude/<recipe>.md`** files from older Personetta installs are removed on `install '*'`. Implemented in `generator/claude_layout.py`.

- **Cline layout (required):** Global rules under **`~/Documents/Cline/Rules/`** (same three `personetta-*.md` files as Claude). Cache: **`.personetta/cline-recipes/<recipe>.md`**. State: **`.personetta/cline-active.json`**. Implemented in `generator/cline_layout.py`.

## R3 — Honor the tools, not the meta-app

- Cursor, Copilot, Claude, Cline, etc. do not “know” about Personetta as a product. **Personetta’s job** is to emit files in the **locations and shapes** those tools actually load, so behavior matches user intent without manual copying.
- Formatter registry and low-level per-recipe paths for tests live in `generator/output_formats.py`. Split layouts: `generator/cursor_layout.py`, `generator/copilot_layout.py`, `generator/claude_layout.py`, `generator/cline_layout.py`. Composed-role text is built in `generator/formatters/` (stable imports also re-exported from `generator/formatter.py`).
- Field merge strategies and tool conflict rules are defined in `config/merge-config.yaml` and applied in `generator/merger.py`.

## R4 — No manual “attach this rule” workflow

- Requiring the user to attach or @-mention a rule for every conversation **defeats the purpose** of pre-authored role definitions.
- **Keystroke economy:** Short phrases (“You are a C# backend developer”) should map to the right **meaning**; the heavy text lives in recipe files. Prefer **`set-active`** to pick the cached recipe so `personetta-active.md` matches the intent without retyping guidelines.
- **Implementation note:** Recipes may define optional **`activation_phrases`** (see recipe schema) for the router; **`description`** remains the primary summary for discovery.

## R5 — This list is the bar for “done”

- Features, refactors, and defaults must be checked against R1–R4.
- If the generator or install story regresses (e.g. baseline/active layout breaks, or global install no longer works), that regression is **priority** to fix.
